# BEACON Hardware Compatibility Guide

Device portability and multi-platform support.

---

## Overview

BEACON uses a **single codebase** with **hardware abstraction** to support multiple device types. You do **NOT** need separate directories for different hardware - the code automatically detects and adapts to the underlying platform.

**Supported Hardware:**
- ✅ Raspberry Pi Zero 2 W
- ✅ Raspberry Pi 4 (2GB/4GB/8GB)
- ✅ Raspberry Pi 5 (4GB/8GB)
- ✅ Intel NUC (N100 or similar)
- ✅ Orange Pi 5 Plus
- ⚠️ Any Debian/Ubuntu-based ARM64 or x86_64 system (with minor tweaks)

---

## What's Device-Agnostic (No Changes Needed)

### ✅ Display Client (100% Portable)
**Files**: `display-client/*`

The HTML/JavaScript display client works on **any** device with a modern Chromium-based browser:
- **No code changes needed**
- Power BI Client library loads from CDN
- Config format identical across all devices
- Responsive to different screen resolutions

**Why it works everywhere:**
- Pure HTML5/ES6 JavaScript
- Browser-based rendering (not hardware-specific)
- No native dependencies

### ✅ Token Service (100% Portable)
**Files**: `token-service/*`

The Node.js token service runs on **any** platform:
- **No code changes needed**
- Runs on laptop, cloud VM, or any server
- Not deployed to the display device itself
- Platform-independent (Windows, Mac, Linux)

## What's Hardware-Aware (Automatic Adaptation)

### 🔧 Hardware Abstraction Layer
**File**: `raspberry-pi/device-detect.sh`

This script automatically:
- Detects device type (Pi Zero 2 W, Pi 4, Pi 5, NUC, Orange Pi, etc.)
- Calculates memory thresholds based on total RAM
- Finds correct Chromium binary for the distro
- Reads CPU temperature using device-specific methods
- Recommends optimal systemd memory limits

**No manual configuration required** - scripts source this automatically.

### 🔧 Installation Script
**File**: `raspberry-pi/install.sh`

**Auto-adapts to:**
- Different Chromium package names (`chromium-browser` vs `chromium`)
- Pi-specific configs (`/boot/config.txt`) - skips if not Raspberry Pi
- Desktop environment paths (handles LXDE-pi and others)
- Memory limits (auto-calculates based on total RAM)

**Changes made:**
- ✅ Removed hard requirement for `vcgencmd` (Pi-specific)
- ✅ Auto-detects hardware on startup
- ✅ Skips Pi-specific optimizations on non-Pi hardware
- ✅ Dynamic memory limit calculation

### 🔧 Watchdog Script
**File**: `raspberry-pi/watchdog.sh`

**Auto-adapts to:**
- **Memory thresholds**: Calculates 85% based on total RAM
  - Pi Zero 2 W (512MB): 435MB threshold
  - Pi 4 (2GB): 1,700MB threshold
  - Pi 5 (4GB): 3,400MB threshold
  - NUC (8GB): 2,000MB threshold (capped, display doesn't need more)
- **Temperature monitoring**: Uses device-specific methods
  - Raspberry Pi: `vcgencmd measure_temp`
  - Intel/Orange Pi: `/sys/class/thermal/thermal_zone0/temp`

**Changes made:**
- ✅ Dynamic memory threshold (was hardcoded 435MB)
- ✅ Device-agnostic temperature reading
- ✅ Graceful fallback if temperature unavailable

### 🔧 Start Script
**File**: `raspberry-pi/start-display.sh`

**Auto-adapts to:**
- **Chromium binary**: Tries `chromium-browser`, `chromium`, `google-chrome`, `chrome`
- Different distro naming conventions

**Changes made:**
- ✅ Auto-detects available browser binary
- ✅ Displays device info on startup for debugging

### 🔧 Systemd Service
**Generated by**: `install.sh`

**Auto-adapts to:**
- Memory limits based on device total RAM
- Automatically set during installation

## Testing Hardware Detection

```bash
# SSH to device
ssh pi@your-device-ip

# Test hardware detection
cd ~/beacon-display/raspberry-pi
source device-detect.sh

# Show all device info
get_device_info

# Test individual functions
detect_hardware                  # Shows: pi-zero-2w, pi-4, pi-5, intel-nuc, etc.
get_memory_total                 # Shows total RAM in MB
```

## Adding Support for New Hardware

**Example: Adding support for ASUS Tinker Board**

1. **Test basic functionality** without changes:
   ```bash
   # Deploy and run install script
   ./scripts/deploy-to-pi.sh tinkerboard-ip
   ssh user@tinkerboard-ip
   cd beacon-display
   sudo raspberry-pi/install.sh
   ```

2. **If installation fails**, update `device-detect.sh`:
   ```bash
   detect_hardware() {
       # ... existing detection ...

       # Add Tinker Board detection
       elif [ -f /proc/cpuinfo ] && grep -qi "Rockchip RK3399" /proc/cpuinfo; then
           echo "tinker-board"

       # ... rest of function ...
   }
   ```

3. **If temperature reading fails**, add to `get_temperature()`:
   ```bash
   get_temperature() {
       DEVICE_TYPE=$(detect_hardware)

       case "$DEVICE_TYPE" in
           tinker-board)
               # Tinker Board specific thermal zone
               if [ -f /sys/class/thermal/thermal_zone1/temp ]; then
                   TEMP_MILLIDEGREE=$(cat /sys/class/thermal/thermal_zone1/temp)
                   awk "BEGIN {printf \"%.1f\", $TEMP_MILLIDEGREE / 1000}"
               else
                   echo "N/A"
               fi
               ;;
           # ... rest of cases ...
       esac
   }
   ```

4. **Test watchdog** to ensure thresholds work correctly:
   ```bash
   cd raspberry-pi
   ./watchdog.sh
   ```

5. **Document** new hardware in this file

## Performance Tuning by Device

### Pi Zero 2 W (512MB RAM)
**Recommendations:**
- Simple dashboards (1-5 visuals)
- 60-second refresh interval
- Single report only
- Avoid map visualizations

**Config adjustments:**
```json
{
  "refreshIntervalSeconds": 60,
  "tokenRefreshMinutes": 50
}
```

### Pi 4 (2GB/4GB) or Pi 5 (4GB/8GB)
**Capabilities:**
- Complex dashboards (10-20+ visuals)
- 30-second refresh interval
- Multi-report rotation (with enhancement)
- Map visualizations supported

**Config adjustments:**
```json
{
  "refreshIntervalSeconds": 30,
  "tokenRefreshMinutes": 50
}
```

### Intel NUC (8GB+)
**Capabilities:**
- Most complex dashboards (25+ visuals)
- Real-time refresh (10-15 seconds)
- 4K displays supported
- Video content in dashboards

**Config adjustments:**
```json
{
  "refreshIntervalSeconds": 15,
  "tokenRefreshMinutes": 50
}
```

## Chromium Package Differences

Different distros use different package names. The `get_chromium_command()` function handles this automatically:

| Distribution | Package Name | Binary Name |
|--------------|--------------|-------------|
| Raspberry Pi OS | chromium-browser | chromium-browser |
| Ubuntu 20.04+ | chromium-browser | chromium-browser |
| Debian 11+ | chromium | chromium |
| Arch Linux | chromium | chromium |
| Fedora/RHEL | chromium | chromium |

**Installation handled by `install.sh`:**
```bash
apt-get install -y chromium-browser  # Works on Raspberry Pi OS, Ubuntu
# OR
apt-get install -y chromium           # Works on Debian
```

**Runtime detection in `start-display.sh`:**
```bash
CHROMIUM_CMD=$(get_chromium_command)  # Auto-finds available binary
```

## OS Compatibility

### ✅ Fully Tested
- Raspberry Pi OS (Debian 11 "Bullseye")
- Raspberry Pi OS (Debian 12 "Bookworm")

### ✅ Should Work (Debian/Ubuntu-based)
- Ubuntu 20.04 LTS / 22.04 LTS / 24.04 LTS
- Debian 11 / 12
- Linux Mint
- Pop!_OS
- Armbian (for Orange Pi)

### ⚠️ Requires Modification
- **Fedora/RHEL**: Change `apt-get` to `dnf/yum`
- **Arch Linux**: Change `apt-get` to `pacman`
- **Alpine Linux**: Change `apt-get` to `apk`

### ❌ Not Supported (Different Architecture)
- Windows (needs PowerShell scripts)
- macOS (needs different setup)
- Android (needs app wrapper)

## Summary: Single Codebase Strategy

**You maintain ONE codebase that:**
1. ✅ Auto-detects hardware on installation
2. ✅ Dynamically calculates resource limits
3. ✅ Gracefully handles missing hardware-specific features
4. ✅ Uses device-agnostic methods where possible
5. ✅ Falls back intelligently when features unavailable

**No separate directories needed unless:**
- Fundamentally different OS (Windows vs Linux)
- Completely different browser (Firefox vs Chromium)
- Different architecture (x86 vs ARM is fine, but Android would need separate code)

**Benefits of this approach:**
- Single `display-client` directory works everywhere
- Bug fixes apply to all hardware simultaneously
- Feature additions benefit all device types
- Simpler maintenance and testing
- Easy to add new hardware support

## Quick Reference

**"Will this work on device X?"**
1. Is it Debian/Ubuntu-based Linux? → Probably yes
2. Does it have 512MB+ RAM? → Yes
3. Can it run Chromium browser? → Yes
4. Then BEACON should work with **zero code changes**

**"Do I need separate code for Pi 4 vs Pi Zero?"**
- No - same code, auto-adapts

**"What if I want to use Pi 5 instead?"**

**"Can I mix hardware types in deployment?"**
- Yes - manage all devices with same codebase and scripts
